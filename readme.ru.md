# Yuki System

Yuki System - это модульная экосистема с открытым исходным кодом для умных устройств и домашней
автоматизации. Она позволяет управлять множеством устройств (ПК, телефонами, IoT-устройствами)
через единый центральный сервер, используя общий протокол, на котором говорит каждый клиент.

Этот репозиторий - **мета-репозиторий**: в нём нет собственного кода, только документация, обзор
архитектуры и ссылки на репозитории всех модулей.

Также доступен на [русском](readme.ru.md) и [日本語](readme.ja.md).

## Обзор

Каждое устройство в экосистеме - клиент удалённого управления для Windows/Linux/Android,
что бы ни появилось следующим - подключается к единому серверу
(`yuki-core`) по WebSocket, аутентифицируется общим токеном и обменивается с ним
статусами/командами/метриками в общем JSON-формате
([`yuki-protocol`](https://github.com/VLPLAY-Games/yuki-protocol)). Администратор управляет всем
этим через веб-панель ([`yuki-webui`](https://github.com/VLPLAY-Games/yuki-webui)): одобряет
новые устройства, отправляет команды, следит за метриками, просматривает журнал аудита, ротирует
токен аутентификации.

Здесь ничто не предполагает облачную инфраструктуру - `yuki-core` - это один Python-процесс,
который вы запускаете в своей собственной сети, а конфигурация по умолчанию (незашифрованный
WebSocket, токен, сгенерированный при первом запуске) рассчитана на то, чтобы сразу заработать в
домашней локальной сети без какой-либо настройки, при этом по-прежнему поддерживая TLS, более
строгую аутентификацию и управление секретами через systemd для тех, кому это нужно.

## Архитектура

```text
                          ┌──────────────┐
                          │  yuki-core   │  Python / asyncio WebSocket-сервер
                          │  («мозг»)    │  ws://host:8000  (/device, /webui)
                          └──────┬───────┘
                 ┌───────────────┼────────────────────────┐
                 │               │                         │
          ┌──────▼─────┐  ┌──────▼──────┐          ┌───────▼────────┐
          │ yuki-webui │  │  Устройства  │          │  yuki-protocol │
          │ Flask +    │  │  (/device)   │          │  общий SDK,    │
          │ JS в       │  │              │          │  свой для      │
          │ браузере   │  └──────┬───────┘          │  каждого языка │
          │ (/webui)   │         │                  └────────────────┘
          └────────────┘         │
                 ┌────────────────┼────────────────────┐
                 │                │                     │
        ┌────────▼───────┐ ┌──────▼───────┐  ┌──────────▼─────────┐
        │ yuki-device-pc │ │ yuki-device- │  │ yuki-device-pc-     │
        │ (Windows, C#)  │ │ android      │  │ linux (Python/      │
        │                │ │ (Kotlin)     │  │ GTK4/libadwaita)    │
        └────────────────┘ └──────────────┘  └──────────────────────┘
```

`yuki-core` - единственный компонент, с которым напрямую взаимодействуют все остальные модули.
Устройства подключаются к `/device`, аутентифицируются общим bearer-токеном и обмениваются
статусами/командами/метриками. Браузеры подключаются к `/webui` (статическую панель управления им
отдаёт Flask-приложение `yuki-webui`) и после аутентификации собственным токеном получают то же
самое представление в реальном времени плюс административные действия (одобрение устройств,
ротация токена, просмотр журнала аудита, ...).

экосистемы в целом.

## Протокол

Весь трафик WebSocket - это JSON, одно сообщение на кадр, без бинарного фрейминга:

```json
{"protocol": "yuki/1.0", "type": "...", "id": "...", "timestamp": 0, "payload": {}}
```

Поле `type` определяет смысл сообщения (`hello`, `welcome`, `status`, `command`,
`command_result`, `metrics`, `device_to_device`, `challenge`, `auth`, ...). Каждая реализация
проверяет, что `protocol` равно ровно `yuki/1.0`, и отклоняет любое другое значение - никакого
механизма совместимости между версиями нет, поэтому в рамках одного развёртывания следует
использовать одну версию протокола повсюду. Полный каталог сообщений, включая оба рукопожатия
аутентификации устройства ниже, см. в README самого
[`yuki-protocol`](https://github.com/VLPLAY-Games/yuki-protocol).

## Модель безопасности

- **Аутентификация устройств**: общий bearer-токен, либо по legacy-схеме (`auth_token` передаётся
  прямо в `hello`), либо через challenge-response (`hello{nonce_c}` → `challenge{nonce_s}` →
  `auth{hmac}`, `hmac = HMAC-SHA256(token, "{nonce_c}:{nonce_s}")`), при котором токен вообще
  никогда не передаётся по сети. `yuki-core` выбирает метод для каждого соединения по наличию
  поля `nonce_c` в `hello` - существующие устройства продолжают работать без изменений, новые
  могут перейти на более надёжное рукопожатие без какой-либо настройки на стороне сервера. В
  обоих случаях сравнение выполняется за постоянное время.
- **Источник токена и его ротация**: токен либо управляется администратором (переменная окружения
  `YUKI_AUTH_TOKEN` или systemd credential через `LoadCredential=yuki_auth_token:...`) - в этом
  случае `yuki-core` никогда не ротирует его сам, - либо генерируется автоматически и хранится в
  `.token` (права доступа 600), ротируясь автоматически каждые `YUKI_TOKEN_ROTATION_HOURS`
  (по умолчанию 24 ч) фоновой задачей, либо по запросу из `yuki-webui`. После любой ротации
  предыдущий токен остаётся действительным ещё `YUKI_TOKEN_GRACE_MINUTES` (по умолчанию 30) минут,
  чтобы устройство, ненадолго оказавшееся офлайн, не оказалось заблокировано прежде, чем получит
  push-уведомление `token_update`.
- **Авторизация устройств**: предъявления корректного токена самого по себе недостаточно - новое
  для `yuki-core` устройство остаётся в очереди на подтверждение, пока администратор не одобрит
  его в `yuki-webui` (либо оно заранее не добавлено в список авторизованных). Устройства также
  можно полностью занести в чёрный список.
- **Вход в WebUI**: `yuki-webui` поставляется с логином по умолчанию `admin`/`admin` (хранится на
  диске в виде хеша, а не открытым текстом) - смените его на панели «Настройки» сразу после
  входа. Собственный сокет браузера `/webui`, работающий в реальном времени, с `yuki-core`
  требует отдельного рукопожатия с токеном (он запрашивается у `yuki-webui` только после того,
  как вы уже вошли в систему) *и* проверки заголовка `Origin` по списку разрешённых значений
  (`YUKI_WEBUI_ALLOWED_ORIGINS` на стороне `yuki-core`, по умолчанию - собственные хост/порт
  `yuki-webui`) - страница, отданная с любого другого origin, не сможет открыть этот сокет, даже
  если каким-то образом раздобудет действительный токен, а сам управляющий сокет вообще
  недостижим для неаутентифицированного браузера.
- **Ограничение частоты запросов (rate limiting)**: `yuki-core` ограничивает число попыток
  рукопожатия по IP-адресу источника (ещё до того, как какой-либо device_id признан доверенным -
  это не даёт одному IP перебирать множество разных device_id, каждый из которых иначе получил бы
  собственную свежую квоту), а также число команд по device_id уже после рукопожатия.
- **Списки разрешённых команд**: каждый клиент (PC, Linux, Android) заявляет, какие
  команды он готов выполнять, и локально отказывается от всего, чего нет в этом списке,
  независимо от того, что разрешает `yuki-core` - скомпрометированный или неправильно
  настроенный сервер не может заставить устройство выполнить команду, которую его владелец явно
  отключил.
- **Шифрование транспорта**: **везде отключено по умолчанию** (обычные `ws://`/`http://`), как и
  положено для типичного развёртывания домашней автоматизации в доверенной локальной сети.
  Каждый компонент поддерживает включение TLS - `yuki-core`
  (`YUKI_TLS_ENABLED`/`YUKI_TLS_CERT`/`YUKI_TLS_KEY`), `yuki-webui`
  (`YUKI_WEBUI_TLS_ENABLED`/...), а настольные и мобильные клиенты - просто через адрес
  `wss://`/`https://` - точные имена переменных см. в
  README каждого модуля. Если TLS явно включён, но настроен неправильно (нет сертификата/ключа),
  и `yuki-core`, и `yuki-webui` отказываются запускаться, а не тихо откатываются к
  незашифрованному соединению - ничто не притворяется зашифрованным, когда это не так. На
  странице «Настройки» `yuki-webui` есть панель Encryption только для чтения, которая показывает
  фактическое текущее состояние - и самой страницы, и её соединения с ядром.
- **Хранение секретов**: токен ядра (когда он хранится в файле) и учётные данные webui хранятся с
  ограниченными правами доступа к файлам (600) и, где это применимо, в виде хеша (пароль webui);
  Windows-клиент шифрует хранимый токен с помощью DPAPI; общий токен никогда не записывается ни в
  одну из баз SQLite.

Ничто из перечисленного не заменяет запуск экосистемы в сети, которой вы действительно доверяете
(ваша домашняя локальная сеть, VPN, ...) - это поднимает планку того, что устройство или браузер
в этой сети могут сделать друг с другом, но не превращает `yuki-core` во что-то безопасное для
прямой публикации в открытый интернет.

## Настройка развёртывания

1. Запустите `yuki-core` (см. его README) - запомните сгенерированный токен в `.token` либо
   задайте `YUKI_AUTH_TOKEN` самостоятельно перед первым запуском.
2. Запустите `yuki-webui`, войдите под `admin`/`admin` и смените пароль в «Настройках».
3. Настройте каждый клиент устройства через его собственный интерфейс, указав адрес `yuki-core`
   и токен из шага 1.
4. Новые устройства появляются в `yuki-webui` в очереди на подтверждение - одобрите их там.
5. При желании включите TLS повсеместно, когда развёртывание уже работает без него - см. README
   каждого модуля.

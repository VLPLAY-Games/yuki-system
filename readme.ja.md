# Yuki System

Yuki System は、スマートデバイスとホームオートメーションのためのオープンソースのモジュール型エコシステムです。
複数のデバイス（PC、スマートフォン、IoT デバイス）を、すべてのクライアントが話す単一の共有プロトコルを使って、
1台の中央サーバーから制御できます。

このリポジトリは**メタリポジトリ**です。それ自体にはコードはなく、ドキュメント、アーキテクチャの概要、そして各モジュール自身のリポジトリへのリンクのみを提供します。`yuki-speaker` は独立した、より古い ESP32 モジュールであり、本ドキュメントおよびエコシステムの 1.0.0 強化作業の対象には含まれていません。

このドキュメントは [русский](readme.ru.md) と [日本語](readme.ja.md) でも利用できます。

## 概要

エコシステム内のすべてのデバイス — Windows/Linux/Android のリモート制御クライアント、ESP32 加湿器、そして今後
登場するものすべて — は、WebSocket 経由で1台のサーバー（`yuki-core`）に接続し、共有トークンで認証した上で、
共通の JSON 形式（[`yuki-protocol`](https://github.com/VLPLAY-Games/yuki-protocol)）でステータス/コマンド/メトリクスを
やり取りします。管理者は Web ダッシュボード（[`yuki-webui`](https://github.com/VLPLAY-Games/yuki-webui)）から
全体を管理します。新しいデバイスの承認、コマンドの送信、メトリクスの監視、監査ログの閲覧、認証トークンの
ローテーションなどが行えます。

ここではクラウドインフラは一切前提としていません — `yuki-core` は自分自身のネットワーク上で動かす単一の
Python プロセスであり、デフォルト設定（平文の WebSocket、初回起動時に生成されるトークン）は、セットアップ不要で
すぐに自宅の LAN で動作するように作られています。それでいて、TLS、より強固な認証、systemd で管理される
シークレットといった、必要な人向けの選択肢もサポートしています。

## アーキテクチャ

```text
                          ┌──────────────┐
                          │  yuki-core   │  Python / asyncio WebSocket サーバー
                          │ (「頭脳」)   │  ws://host:8000  (/device, /webui)
                          └──────┬───────┘
                 ┌───────────────┼────────────────────────┐
                 │               │                         │
          ┌──────▼─────┐  ┌──────▼──────┐          ┌───────▼────────┐
          │ yuki-webui │  │  デバイス    │          │  yuki-protocol │
          │ Flask +    │  │  (/device)   │          │  言語ごとの    │
          │ ブラウザJS │  │              │          │  共有SDK       │
          │ (/webui)   │  └──────┬───────┘          │                │
          └────────────┘         │                  └────────────────┘
                 ┌────────────────┼─────────────────────┬───────────────┐
                 │                │                     │               │
        ┌────────▼───────┐ ┌──────▼───────┐  ┌──────────▼────────┐ ┌────▼─────────────┐
        │ yuki-device-pc │ │ yuki-device- │  │ yuki-device-pc-   │ │ yuki-humidifier   │
        │ (Windows, C#)  │ │ android      │  │ linux (Python/    │ │ (ESP32-C3, C++)   │
        │                │ │ (Kotlin)     │  │ GTK4/libadwaita)  │ │                   │
        └────────────────┘ └──────────────┘  └────────────────────┘ └───────────────────┘
```

`yuki-core` は、他のすべてのモジュールが直接やり取りする唯一のコンポーネントです。デバイスは `/device` に
接続し、共有のベアラートークンで認証した上で、ステータス/コマンド/メトリクスをやり取りします。ブラウザは
`/webui`（`yuki-webui` の Flask アプリが配信する静的ダッシュボード）に接続し、自身のトークンで認証した後、
デバイスと同じリアルタイムビューに加えて管理操作（デバイスの承認、トークンのローテーション、監査ログの
閲覧、...）を利用できます。

## プロトコル

すべての WebSocket 通信は JSON で、1フレームにつき1メッセージ、バイナリフレーミングはありません。

```json
{"protocol": "yuki/1.0", "type": "...", "id": "...", "timestamp": 0, "payload": {}}
```

`type` はメッセージの意味を選択します（`hello`、`welcome`、`status`、`command`、`command_result`、
`metrics`、`device_to_device`、`challenge`、`auth`、...）。すべての実装は `protocol` が正確に `yuki/1.0`
であることを検証し、それ以外を拒否します — バージョン間の互換性を吸収する仕組みは存在しないため、1つの
デプロイではどこでも同じプロトコルバージョンを使用する必要があります。メッセージの完全な一覧（下記の
2種類のデバイス認証ハンドシェイクを含む）については、[`yuki-protocol`](https://github.com/VLPLAY-Games/yuki-protocol)
自身の README を参照してください。

## セキュリティモデル

- **デバイスの認証**: 共有のベアラートークンを使用します。従来どおり `hello` に `auth_token` を直接含めて
  送る方式、またはチャレンジレスポンス方式（`hello{nonce_c}` → `challenge{nonce_s}` → `auth{hmac}`、
  `hmac = HMAC-SHA256(token, "{nonce_c}:{nonce_s}")`）のいずれかで、後者はトークンを一切ネットワーク上に
  流しません。`yuki-core` は `hello` に `nonce_c` が含まれているかどうかに基づいて接続ごとに方式を選択します
  — 既存のデバイスはそのまま変更なく動作し続け、新しいデバイスはサーバー側の設定変更なしでより強固な
  ハンドシェイクを選べます。いずれの方式でも、比較には定数時間比較を使用します。
- **トークンのソースとローテーション**: トークンは管理者が管理する方式（`YUKI_AUTH_TOKEN` 環境変数、または
  `LoadCredential=yuki_auth_token:...` による systemd クレデンシャル — この場合 `yuki-core` はトークンを
  自動ローテーションしません）か、自動生成されて `.token`（パーミッション 600）に保存される方式のいずれかで、
  後者はバックグラウンドタスクにより `YUKI_TOKEN_ROTATION_HOURS`（デフォルト 24 時間）ごとに自動的に
  ローテーションされるほか、`yuki-webui` からオンデマンドでローテーションすることもできます。ローテーション後も、
  直前のトークンは `YUKI_TOKEN_GRACE_MINUTES`（デフォルト 30 分）の猶予期間中は有効なままなので、一時的に
  オフラインだったデバイスが `token_update` の通知を受け取る前に締め出されることはありません。
- **デバイスの認可**: 有効なトークンを提示するだけでは不十分です — `yuki-core` にとって未知のデバイスは、
  管理者が `yuki-webui` から承認するまで保留状態に置かれます（あるいは、あらかじめ認可済みデバイス群に
  登録されている場合を除きます）。デバイスを完全にブラックリストへ登録することもできます。
- **WebUI のログイン**: `yuki-webui` はデフォルトで `admin`/`admin` のログイン情報を持っています（ディスク上
  ではハッシュ化されており平文ではありません）— ログイン後はダッシュボードの設定パネルから変更してください。
  ブラウザから `yuki-core` へのリアルタイム `/webui` ソケットには、独自のトークンハンドシェイク（ログイン後に
  のみ `yuki-webui` から取得できます）*に加えて*、許可リストに登録された `Origin` ヘッダー（`yuki-core` 側の
  `YUKI_WEBUI_ALLOWED_ORIGINS`、デフォルトは `yuki-webui` 自体のデフォルトのホスト/ポート）が必要です —
  それ以外の場所から配信されたページは、たとえ何らかの方法で有効なトークンを入手していたとしても、その
  ソケットを開くことはできず、未認証のブラウザからは制御プレーンのソケットに一切到達できません。
- **レート制限**: `yuki-core` は、送信元 IP ごとにハンドシェイクの試行回数を制限します（device_id がまだ
  信頼されていない段階での制限であり、1つの IP が多数の device_id に対して総当たり攻撃を試み、device_id
  ごとに新しいクォータを得てしまうのを防ぎます）。ハンドシェイク後は、device_id ごとにコマンドの実行回数も
  制限します。
- **コマンド許可リスト**: すべてのクライアント（PC、Linux、Android、加湿器）は、自分が実行してもよい
  コマンドを通知し、そのリストにないコマンドは `yuki-core` が何を許可しているかに関わらず*ローカルで*
  拒否します — これにより、侵害されたサーバーや設定ミスのあるサーバーであっても、デバイスの所有者が
  明示的に無効化したコマンドを実行させることはできません。
- **通信の暗号化**: **どこでもデフォルトではオフ**です（平文の `ws://`/`http://`）。これは、信頼された
  LAN 上での典型的なホームオートメーションのデプロイに合わせたものです。すべてのコンポーネントで TLS を
  任意に有効化できます — `yuki-core`（`YUKI_TLS_ENABLED`/`YUKI_TLS_CERT`/`YUKI_TLS_KEY`）、`yuki-webui`
  （`YUKI_WEBUI_TLS_ENABLED` など）、`yuki-humidifier`（`Config.h` 内の `ENABLE_TLS`）、そしてデスクトップ/
  モバイルクライアントでは単に `wss://`/`https://` のアドレスを使うだけです — 正確な変数名は各モジュール
  自身の README を参照してください。TLS が明示的に有効化されているにもかかわらず設定に不備がある場合
  （証明書や鍵が見つからないなど）、`yuki-core` と `yuki-webui` はどちらも、平文へ黙ってフォールバックする
  のではなく起動を拒否します — 暗号化されていない状態を暗号化されているかのように見せかけることは
  ありません。`yuki-webui` の設定ページには、ページ自身とそのコア接続の両方について現在の状態を示す
  読み取り専用の暗号化パネルがあります。
- **保存データの秘密情報**: core のトークン（ファイルベースの場合）と webui の認証情報は、制限的な
  ファイルパーミッション（モード 600）で保存され、該当する場合はハッシュ化されます（webui のパスワード）。
  Windows クライアントは、保存するトークンを DPAPI で暗号化します。また、共有トークンがいずれの SQLite
  データベースにも書き込まれることはありません。

これらはいずれも、実際に信頼できるネットワーク（自宅の LAN、VPN など）でエコシステムを運用することの
代わりにはなりません — 同じネットワーク上のデバイスやブラウザが互いに対して何をできるかのハードルを
上げるものであり、`yuki-core` をインターネットに直接公開しても安全なものに変えるわけではありません。

## デプロイのセットアップ

1. `yuki-core` を起動します（README を参照）— `.token` に生成されたトークンを控えるか、初回起動前に
   自分で `YUKI_AUTH_TOKEN` を設定してください。
2. `yuki-webui` を起動し、`admin`/`admin` でログインした後、設定からパスワードを変更してください。
3. 各デバイス（加湿器は自身の AP セットアップページから、PC/Linux/Android クライアントは各自の UI から）に、
   `yuki-core` のアドレスと手順1のトークンを設定してください。
4. 新しいデバイスは `yuki-webui` 上に保留状態として表示されます — そこで承認してください。
5. 他の部分が問題なく動作するようになったら、任意で各モジュールの README に従ってすべての箇所で TLS を
   有効にしてください。
